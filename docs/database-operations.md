# Database operations

The ordered migrations create exactly seven public domain tables. Contract/default/registry SQL is generated by `node scripts/generate-sql-contract.mjs`; regenerate after changing the shared JSON schemas. Applied migrations are never edited, so `0004` holds the original contract and the generator rewrites (and `--check` verifies) only the marked block of the newest migration that layers changes on it (`0019_model_fields.sql`, which layers the model fields on `0017_site_links.sql`'s `site_links` kind; it also checks that storage references name the entry's own company); `--check` also fails if a schema not replaced there drifts from the frozen `0004` copy. A new contract change needs a new migration with its own marked block. The protected SQL validates strict nested shapes, stable paths, origin rules, immutable evidence, cross-entry claim support, and complete approved snapshot manifests. `private` must remain outside the exposed Data API schemas.

Use a migration administrator connection with `DATABASE_URL=... node scripts/migrate.mjs`. The runner defaults to database names ending `_test`; a deployment operator must explicitly pass `--allow-production` for another target. It records exact applied source in Supabase's separate `supabase_migrations` infrastructure schema, serializes concurrent runners, and rejects edited applied migrations. Supabase Auth (`auth.users`, `auth.uid()`) and `anon`/`authenticated` roles must exist first. `tests/db/bootstrap.sql` supplies a small disposable-test shim; never use it in Supabase or a native real-Auth stack.

Tables/functions belong to `moflo_owner NOLOGIN`. The dedicated worker connection login must receive membership in `moflo_worker`, which has only schema usage and the six protected worker operations. It has no direct table privileges. `claim_job` returns a JSON resume bundle containing the job, finalized `source_captures`, and `current_entries` summaries. No elevated credentials belong in browser environment variables. User RPCs retain the verified caller JWT so `auth.uid()` remains the author and authorization identity.

`TEST_DATABASE_URL=..._test npm run db:test` runs representative native PostgreSQL acceptance. The suite creates and drops its own uniquely named disposable database, with separate authenticated/viewer/nonmember/worker sessions. It does not alter the selected baseline database. The migration login needs `CREATEDB`; its role-creation ability is used only if the application roles do not already exist. PostgreSQL17 is verified locally; hosted Supabase and release deployment remain separate qualification gates.

All writes to a draft, membership or publication lock the company first. Direct name-only updates also recheck membership after acquiring the row lock, because an RLS predicate evaluated before waiting can otherwise outlive a committed revocation. Source captures, revisions and snapshots reject UPDATE/DELETE. Entry revision validation is a deferred security-definer constraint trigger, allowing a first-import batch to validate generated claims against same-job sibling revisions in the same transaction; a failed validator rolls back the entire batch.

The consolidated migration/test layout implements the database Quests as shared coherent modules instead of repeating a migration and test harness per Quest. SQL/default parity is tested against the TypeScript assembler on manual and conflict-selected publication paths. Evidence and native tooling live outside the repository under the task work directory.

A usable first import requires all five singleton candidates and creates them atomically; empty repeatable entities are rejected. A no-usable-result job creates no entries. Proposal application copies only explicitly selected registered field targets or selected stored conflict values. It preserves every unselected current value, claim and coverage assessment. Ordinary proposed fields carry only immutable {id,target} change metadata; their values and provenance remain in the recorded proposal. Saved provenance retains the selected or current origin.

The bounded resume schema in `supabase/generated/worker-checkpoint.schema.json` follows `src/worker/crawl/frontier.ts`, `budgets.ts`, `run-crawl.ts`, and `src/worker/extract/pipeline.ts`: frontier URLs/depths/aliases, consumed budgets, safe errors, same-job captured/extracted source IDs and compact validated candidates. It is merged into generated SQL. `node scripts/generate-sql-contract.mjs --check` rejects stale artifacts. Checkpoints may be partial objects while a job starts; any supplied field has its complete strict type.

Membership validation relies on existing Auth foreign keys rather than selecting the RLS-protected Auth roster. Even removal of a valid non-member performs a transactional FK check without leaving a membership behind. The domain owner has no Auth-user SELECT grant.

Extracted gender requires a cited captured text excerpt containing explicit self-description and the selected original wording. A provenance note alone does not establish source support. User-provided gender still requires the actor/time and explicit attestation note.

Draft saves may retain source origin when the user explicitly selects an exact candidate from the prior stored conflict. The protected edit validator verifies that stored candidate, selected value, actor, origin and evidence; an invented caller-side candidate does not establish source support.

Deleting a key person or an offering (migration `0020_entry_archive.sql`) is an archive, not an erase. `public.archive_entry(company, entry, expected_revision, request)` locks the company like every draft write (owner or editor of a live company; a non-member finds nothing, a viewer is forbidden, an archived company is refused), refuses the five singleton kinds, checks the expected revision (`stale_revision`, with the current one) and sets a permanent tombstone on `knowledge_entries` (`archived_at`, `archived_by`, `archive_request_id`; nothing else can set or change it). The same request on the same entry is answered again without a second change; another request finds the entry gone. Every revision stays, saved versions keep the entry, and revisions remain immutable. An archived entry is invisible to members (the `tenant_read` policies of `knowledge_entries` and `knowledge_entry_versions`), so drafts, history and the editor no longer see it; publication (`assemble_snapshot`, the snapshot manifest check and `publish_knowledge_base`) and the worker's `current_entries` read live entries only; and a trigger on `knowledge_entry_versions` refuses any new revision of an archived entry, whichever function writes it. The deletion raises the company's draft generation. `finish_job` still counts archived entries when it decides whether an import is the first one, so deleting every person never turns a later crawl into a first import.
